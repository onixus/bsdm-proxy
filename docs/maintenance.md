# Поддержка документации

## Источник истины

Каноническая документация хранится в этом репозитории:

- `README.md` — краткое введение и быстрый старт;
- `docs/project-status.md` — фактическая зрелость функций;
- `docs/getting-started/` — установка и пилот;
- `docs/architecture/` — устройство и capacity planning;
- `docs/features/` — функциональные модули;
- `docs/analytics/` — ClickHouse, alerting и ML;
- `docs/ops-and-dev/` — эксплуатация и разработка;
- `docs/roadmap.md` — только будущие планы.

GitHub Wiki является публикуемым представлением канонической документации:

- все поддерживаемые страницы из `docs/` публикуются как зеркала;
- `Home`, тематические landing pages, sidebar и footer генерируются отдельно;
- release notes автоматически добавляются при появлении нового файла;
- машинные raw-результаты load test остаются ссылками на основной репозиторий.

Не исправляйте сгенерированные страницы только в Wiki: изменение будет потеряно
при следующей синхронизации.

## Требования к изменениям

Документация изменяется в том же PR, что и пользовательская функция.

Перед commit:

```bash
python3 scripts/check-doc-links.py
python3 scripts/sync-wiki.py --validate
```

Если изменяется структура Wiki:

```bash
python3 scripts/sync-wiki.py /path/to/bsdm-proxy.wiki
python3 scripts/sync-wiki.py /path/to/bsdm-proxy.wiki --check
```

`--validate` проверяет, что каждый Markdown-документ покрыт Wiki catalog, что в
нём нет дублей и что внутренние ссылки генерируемых страниц разрешаются.
`--check` завершается с ошибкой при drift клонированной Wiki.

Документ без курируемой записи в `PAGES` подхватывается автоматически: заголовок
берётся из первого `#`, имя Wiki-страницы — из пути под `docs/`, а раздел — из
первого каталога (см. `DERIVED_SECTIONS`); неизвестный каталог попадает в раздел
«Прочие документы». Поэтому новый файл в `docs/` не роняет docs job — он просто
публикуется с типовым описанием.

Генератор удаляет только устаревшие страницы со служебным generated marker.
Ручная страница без marker не удаляется автоматически.

## Версии и статусы

- Текущую версию берите из `proxy/Cargo.toml`.
- Исторические номера версий остаются только в `docs/releases/`.
- Метки «основной», «beta» и «experimental» определены в
  `docs/project-status.md`.
- Наличие модуля или UI-страницы не означает production-ready.
- Roadmap не является доказательством реализации.

## Гигиена трекера

Правила выведены из разбора августа 2026 (эпик #324 был закрыт при 8 открытых
подзадачах). Исторический контекст — [improvement-proposal-2026-08.md](improvement-proposal-2026-08.md).

1. **Зонтичный issue закрывается последним.** Не писать `Closes`/`Fixes` на epic
   в теле PR: GitHub закроет его автоматически в момент мержа, независимо от
   состояния подзадач. Эпик закрывается вручную, после последней подзадачи, с
   отметкой success criteria.
2. **PR закрывает issue явно.** PR, реализующий issue, обязан содержать
   `Closes #N`. Иначе задача остаётся открытой при готовом коде, и трекер
   расходится с `main`.
3. **ADR-issue закрывается при мерже ADR-файла**, а не при реализации решения.
4. **Закрытие с частичным результатом сопровождается передачей остатка**: в
   закрывающем комментарии заводятся issue на невыполненное (образец — #313,
   передавший остаток в #338/#339).

## Планировочные документы и срок годности

`project-status.md` и `roadmap.md` — живые и обновляются в том же PR, что и код.
Разовые аналитические записки (ревизии приоритетов, предложения по улучшению)
живут иначе:

1. Имя содержит дату среза (`improvement-proposal-2026-08.md`).
2. Как только записка применена или устарела — в её начало добавляется блок
   **ИСТОРИЧЕСКИЙ ДОКУМЕНТ** со ссылками на актуальные источники. Устаревшая
   записка без такого блока опаснее отсутствия документа: по ней планируют работу,
   которой нет.
3. Долгоживущие выводы (правила процесса) переносятся сюда, а не остаются в записке.
4. Утверждения о состоянии трекера имеют срок годности в дни. Перед планированием
   по такому документу — сверка с `gh issue list --state open`.

## Ссылки

- Внутри `docs/` используйте относительные ссылки с учётом текущего каталога.
- На файлы вне `docs/` также используйте корректный относительный путь.
- В Wiki ссылки преобразуются автоматически.
- При добавлении новой страницы добавьте запись в catalog `scripts/sync-wiki.py`:
  без неё страница всё равно опубликуется, но с автогенерированным описанием и,
  для нового каталога, в разделе «Прочие документы».
- Не добавляйте ссылки на старые имена файлов ради совместимости: вместо этого
  обновляйте все места использования.
